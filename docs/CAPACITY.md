# 16 核 / 32GB 的 CPU 本地容量调优

起始值：应用 CPU 上限 8 核、内存上限 12GB、后台 OCR 并发 2、每个 Tesseract 2 线程。保留容量给系统、缓存、浏览器和未来服务。无需 GPU。

1. 先以单个虚构文本 PDF 验证链路，再用 5/10/20 页扫描样本验证 OCR
2. 收集每份报告排队时间、处理时间和峰值内存，检查是否因页数/OCR 页上限被截断
3. 使用 `docker stats`、`docker compose logs` 和 `/api/health` 查看状态，不在日志中加入正文
4. 在受控环境用自己的脱敏代表性样本分别以 1、2、4 份并发上传测量 P50/P95
5. 如 CPU 仍有余量且内存稳定，逐步增加后台并发；不要同时盲目提高每个 OCR 的线程数
6. 大文件先拆分。增加页数上限时同步测量延迟与内存；队列越长不代表吞吐更高
7. 对 32GB 机器建议持续保留至少 8GB 系统余量，并留意 Docker/SQLite 存储空间

后台队列限制的是同时进行的解析工作；上传请求、PDF 解析器及 DOCX 解压仍可能消耗内存。默认上传 20MiB，PNG 像素限制，DOCX 解压体积/条目限制、原生命令超时共同降低风险，但不替代防病毒或隔离沙箱。

本交付未在目标 16 核/32GB 上做压力测试；没有承诺“每分钟 X 份”或最大用户数。生产实例前应额外测量重启、异常任务和磁盘满的恢复行为。
